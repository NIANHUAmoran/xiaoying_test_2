# 最难问题、学习收获与下一步

难点是重规划时既能换候选，也不能遗忘已花费用和成功结果。实现把“候选估算”“实际费用账本”“当前步骤状态”“历史尝试”“最终方案”分开：估算不扣费；成功生成后换候选不能退款；失败尝试保持失败事件；续跑成功更新当前步骤而不删除旧事件。

骨架先跑通正常路径，再补预算与时间、失败注入、事务幂等和续跑。测试特别检查了 SQLite 写入失败后只回滚保存步骤、先前脚本和费用仍保留；两个连接执行同一步只有一次实际收费；保存完成后冻结付费动作，防止模型继续执行导致已保存方案费用与账本不一致。

真实模型表现和离线策略不完全相同：一次生成失败后，离线策略选择 lean 替代方案，真实模型观察 retryable 后选择重试 premium。两者都保留已成功检索结果且遵守预算、时间；分别记录实际路径，比硬把真实结果描述成预设路径更可核查。超预算路径则实际显示模型从 12 改选 8，是本题的重要证据。

时间缺口的计算也需要包含尚未执行的检索步骤，不能只算生成和保存。实现已统一按“当前已耗时 + 剩余依赖步骤”估算，并覆盖截止时间早于起点和恰好赶上截止时间的边界。

实现及验证时间窗口、当前完成范围见 [delivery-status.json](../examples/delivery-status.json)。记录包含本次 AI 实现与实际验证等待，不代表候选人个人用时；本人实际总投入和亲自复核内容应在最终提交前补充。

下一步优先由候选人复核三条真实 Trace 与费用账本，再根据需求补充多任务依赖图、并行调度和更多候选。若业务工具接真实付费服务，需要增加外部幂等与资源预留，模拟时钟也需接入真实时钟。当前尚待填写 GitHub URL、最终 commit SHA 与评审访问权限，不宣称已远程提交。
